## 2. Bug Analysis & Root Cause ("Where the AI Was Wrong")

In client interviews and code audits for this project, one explicit requirement for the handover note is:
> *"one place the AI was wrong, and how you checked it works."*

This task addresses the primary architectural bug generated by the initial AI prototype.

### 2.1 The Root Cause: Naive Booking Existence Check
In the original implementation of `server/src/utils/helpers.ts`:

```typescript
export function isSeatBookable(seat: Seat & { bookings: Booking[] }, event: Event): boolean {
  if (new Date(event.startsAt) < new Date()) {
    return false;
  }
  return seat.bookings.length === 0; // ⚠️ ROOT CAUSE: Assumes ANY booking blocks the seat!
}
```

And in `server/src/services/eventService.ts`:

```typescript
export async function listEvents() {
  const events = await prisma.event.findMany({
    orderBy: { startsAt: 'asc' },
    include: { seats: { include: { bookings: true } } }, // ⚠️ Fetches CANCELLED bookings too!
  });

  return events.map((event) => {
    const seatsLeft = event.seats.filter((seat) => isSeatBookable(seat, event)).length;
    return {
      id: event.id,
      title: event.title,
      venue: event.venue,
      startsAt: event.startsAt,
      price: formatPrice(event.priceCents),
      totalSeats: event.seats.length,
      seatsLeft,
    };
  });
}
```

### 2.2 Why the AI Was Wrong
1. **Ignored Booking Lifecycle States:** When an attendee cancels a booking (`POST /bookings/:id/cancel`), the application does not hard-delete the row from PostgreSQL. Instead, it transitions `status` from `'CONFIRMED'` to `'CANCELLED'`. Because the booking record remains in the database, `seat.bookings.length` is `1` (or more).
2. **Permanent Seat "Leak":** Because `isSeatBookable` checked `seat.bookings.length === 0`, any seat that was booked and subsequently cancelled was permanently classified as unbookable by `listEvents()`. The `seatsLeft` counter on the events catalogue decreased and **never recovered**.
3. **Endpoint Discrepancy & Grid Contradiction:**
   - In `getEventWithSeats(req)` (`GET /events/:id`), the AI originally wrote:
     ```typescript
     seats: {
       orderBy: [{ row: 'asc' }, { col: 'asc' }],
       include: { bookings: { where: { status: 'CONFIRMED' } } },
     }
     ```
   - On the event detail page, `seat.bookings.length === 0` evaluated to `true` for cancelled seats, rendering them as available purple seats.
   - However, on the home page event cards (`GET /events`), `seatsLeft` counted those seats as unavailable.
   - For example, in the seeded event "Postgres in Practice" (40 seats, 2 confirmed bookings, 1 cancelled booking):
     - **Catalogue (`GET /events`):** Reported `37 seats left` (wrong! 40 - 3 bookings = 37).
     - **Grid (`GET /events/1`):** Showed 38 available seats and allowed booking Seat A3.
4. **Past Event Inconsistency on Detail Page:**
   - `listEvents` used `isSeatBookable`, so past events had `seatsLeft: 0`.
   - `GET /events/:id` naively checked `seat.bookings.length === 0` instead of calling `isSeatBookable(seat, event)`. As a result, past events showed seats as available and clickable on the detail view, only to fail with a `400` error when attempting to submit a booking.

## 3. Comprehensive Fix Strategy

### 3.1 Domain Helper Hardening (`server/src/utils/helpers.ts`)
Updated `isSeatBookable` to enforce:
1. Event start time validation: If `event.startsAt` is in the past, return `false`.
2. Safe navigation for empty or undefined `seat.bookings`.
3. Status inspection: Only bookings with `status === 'CONFIRMED'` block availability.
4. Structural typing to support both Prisma models and mock plain objects in unit tests:
```typescript
export function isSeatBookable(
  seat: { bookings?: Array<Pick<Booking, 'status'>> | null },
  event: Pick<Event, 'startsAt'> | { startsAt: Date | string }
): boolean {
  if (new Date(event.startsAt) < new Date()) {
    return false;
  }
  if (!seat.bookings || seat.bookings.length === 0) {
    return true;
  }
  return !seat.bookings.some((booking) => booking.status === 'CONFIRMED');
}
```

### 3.2 Query Optimization in Service Layer (`server/src/services/eventService.ts`)
In `listEvents()`, added a filter in Prisma's relational `include`:
```typescript
include: {
  seats: {
    include: {
      bookings: {
        where: { status: 'CONFIRMED' },
      },
    },
  },
}
```
This delivers a two-fold benefit:
- Reduces memory and payload overhead by not pulling historical cancelled records from PostgreSQL into the Node.js process.
- Provides defense-in-depth: Even if raw records were pulled, `isSeatBookable` verifies `booking.status === 'CONFIRMED'`.

### 3.3 Route Unification (`server/src/routes/events.ts`)
Unified `GET /events/:id` to compute seat availability using the exact same domain helper:
```typescript
const seats = event.seats.map((seat) => ({
  id: seat.id,
  row: seat.row,
  col: seat.col,
  label: seat.label,
  available: isSeatBookable(seat, event),
}));
```
Both endpoints now share a single source of truth for seat availability and past event status.
